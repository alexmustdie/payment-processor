## Что проверяют тесты

1. API: создание/чтение, авторизация, валидация, неизвестный UUID,
   повтор ключа с тем же и другим телом, нормализация денежной суммы.
2. Конкурентность: 20 одновременных HTTP-запросов дают один платеж и одно событие;
   два обработчика одного события вызывают шлюз и webhook один раз.
3. Атомарность: ошибка вставки outbox откатывает платеж.
4. Шлюз: обе ветки `succeeded`/`failed`; технические исключения доходят до DLQ.
5. Webhook: `204`, `503`, таймаут, redirect; три попытки, задержки 2/4 секунды,
   сохранение результата шлюза и стабильного ключа уведомления.
6. Сбои: прерывание после коммита результата шлюза, повтор события после обработки,
   отказ публикации, сбой после broker confirm до коммита outbox.
7. Relay: `SKIP LOCKED` для параллельных издателей, запрет ранней публикации retry.
8. Consumer: неверная схема сообщения, ошибка хранилища, отмена при остановке.
9. Граничные JSON-значения: вложенные NaN/Infinity, NUL и некорректный Unicode
   в строках и ключах дают корректный `422`, не создавая платеж/outbox;
   валидные вложенные данные с Unicode сохраняются без изменений.
10. Webhook ограничен общим временем HTTP-операции; ненужное тело ответа
    не скачивается. Медленные заголовки приводят к сохранению retry.
11. Отмена consumer во время инфраструктурной паузы выполняет NACK/requeue,
    а не ошибочную отправку в DLQ.

## Сквозной сценарий с настоящими сервисами

1. HTTP API -> PostgreSQL -> outbox -> RabbitMQ -> consumer -> HTTP webhook.
2. Повтор POST и конфликт Idempotency-Key.
3. Успешный webhook с первой попытки.
4. Две ошибки webhook, затем успех с третьей попытки; проверяются реальные
   интервалы между запросами и неизменность payload.
5. Три ошибки webhook, затем наличие сообщения в очереди `payments.dead`.
6. Повторная публикация обработанного события не создаёт новых HTTP-вызовов.
7. Невалидное сообщение поступает в DLQ через dead-letter exchange.
8. RabbitMQ остановлен: API отвечает `202`, событие остаётся в outbox;
   после запуска брокера платеж завершается.
9. Consumer получает SIGKILL после поступления webhook получателю, до HTTP-ответа.
   После запуска сообщение доставляется повторно; `processed_at`, результат
   шлюза и содержимое webhook сохраняются, завершённая попытка учитывается один раз.

Команды воспроизведения приведены в README. Тестовая БД отделена от основной.
Гарантия HTTP-доставки - at least once: в пункте 9 повторный webhook ожидаем
и подтверждает необходимость дедупликации у получателя.
