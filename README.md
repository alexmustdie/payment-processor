# Асинхронный процессинг платежей

Тестовое задание: FastAPI, Pydantic v2, асинхронный SQLAlchemy 2, PostgreSQL,
RabbitMQ/FastStream, Alembic, Docker Compose. Python 3.12. Точные версии зависимостей
зафиксированы в `uv.lock`.

Сервис принимает платеж, сохраняет его вместе с событием в одной транзакции,
обрабатывает через эмулятор шлюза и доставляет результат на webhook.

## Запуск

Нужны Docker с Compose v2 и Python 3 для генерации локального API-ключа.
Команды выполняются из корня проекта. Реальные секреты для запуска не нужны.

```sh
python3 scripts/create_env.py
docker compose --profile demo up -d --build --wait
docker compose ps -a
```

`create_env.py` создаёт `.env` со случайным ключом, правами `0600` и не выводит ключ.
Существующий `.env` не перезаписывается. `.env` исключён из Git, Docker-контекста
и архива решения. Логин и пароль `payments` в Compose являются демонстрационными,
предназначены только для этого локального стенда.

Сервисы:

| Сервис | Назначение | Адрес на хосте |
| --- | --- | --- |
| `postgres` | Платежи и outbox, постоянный volume | `127.0.0.1:55432` |
| `rabbitmq` | Durable очереди и обменники, постоянный volume | `127.0.0.1:5673` |
| RabbitMQ Management | Просмотр очередей; demo-логин/пароль `payments` | http://127.0.0.1:15673 |
| `migrate` | Однократный `alembic upgrade head` перед API/consumer | - |
| `api` | HTTP API и фоновый outbox relay | http://127.0.0.1:18080 |
| `consumer` | Единственный обработчик платежей | - |
| `webhook` | Необязательный локальный получатель, профиль `demo` | http://127.0.0.1:18081 |

`migrate` со статусом `Exited (0)` означает успешное применение миграции.
Без демонстрационного webhook: `docker compose up -d --build --wait`.
API и демонстрационный получатель имеют HTTP healthcheck; `--wait` дожидается
готовности сервисов. Сквозной скрипт также проверяет готовность перед запросами.
Все опубликованные порты привязаны к loopback. Доступность RabbitMQ не блокирует
запуск API: если брокер недоступен, новые события остаются в PostgreSQL.

## Примеры API

Из корня проекта загрузите сгенерированный ключ в текущий shell, не выводя его:

```sh
set -a
source .env
set +a
```

Создание платежа:

```sh
curl -i http://127.0.0.1:18080/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H 'Idempotency-Key: order-42' \
  -H 'Content-Type: application/json' \
  -d '{"amount":"125.50","currency":"RUB","description":"Order 42","metadata":{"order_id":42},"webhook_url":"http://webhook:8001/ok"}'
```

Ответ: `202 Accepted`, поля `payment_id`, `status`, `created_at`. Используйте
полученный `payment_id` вместо `UUID_ИЗ_ОТВЕТА`:

```sh
curl http://127.0.0.1:18080/api/v1/payments/UUID_ИЗ_ОТВЕТА \
  -H "X-API-Key: $API_KEY"
```

Повтор того же запроса с тем же ключом возвращает тот же платеж и его текущий
статус, без новой записи outbox. Суммы `10`, `10.0`, `10.00` считаются одинаковыми.
Другой запрос с занятым ключом получает `409 Conflict`. Гонка запросов разрешается
уникальным ограничением PostgreSQL и `INSERT ... ON CONFLICT DO NOTHING`.
Ключ ограничен 255 печатными ASCII-символами без пробелов.

Сумма строго положительная, до 16 цифр перед точкой и 2 после; валюты `RUB`, `USD`,
`EUR`. В JSON-ответах денежные суммы представлены строками, без потери точности.
Описание ограничено 2000 символами. Лишние поля запрещены. `webhook_url` принимает
HTTP/HTTPS, без логина, пароля и fragment. `metadata` - JSON-объект.
Строки и вложенные JSON-значения проверяются на совместимость с PostgreSQL:
NUL, некорректный Unicode и бесконечные/NaN числа получают `422` до записи в БД.
Ответ валидации содержит тип ошибки, путь и сообщение, без исходного ввода.

Коды ошибок: `401` для отсутствующего/неверного `X-API-Key`, `404` для неизвестного
платежа, `409` при конфликте ключа, `422` при невалидном запросе или отсутствии
`Idempotency-Key`. Все эндпоинты основного API, включая `/docs` и `/openapi.json`,
требуют API-ключ. Для Swagger в браузере нужен клиент, добавляющий заголовок
`X-API-Key` и к странице, и к запросу схемы; обычное открытие `/docs` даст `401`.
Схему можно получить напрямую:

```sh
curl http://127.0.0.1:18080/openapi.json -H "X-API-Key: $API_KEY"
```

## Обработка, retry и DLQ

1. API одной транзакцией создаёт `payments` со статусом `pending` и `outbox`
   с событием `{payment_id, attempt: 1}` для `payments.new`.
2. Relay в lifespan API выбирает наступившие события через
   `FOR UPDATE SKIP LOCKED`, публикует persistent-сообщение с `mandatory=True`
   и publisher confirms. Только после подтверждения выставляет `published_at`
   и коммитит. На ошибке строка остаётся неопубликованной.
3. Один FastStream consumer читает `payments.new`. У очереди
   `x-single-active-consumer=true`, у канала `prefetch_count=1`. Даже при случайном
   запуске второй реплики одновременно активен один consumer.
4. Consumer под блокировкой строки эмулирует шлюз: случайная задержка 2-5 секунд,
   90% `succeeded`, 10% `failed`. Результат и `processed_at` коммитятся до webhook.
   Отказ шлюза `failed` является конечным бизнес-результатом, о нём тоже отправляется
   webhook; сам по себе он не ведёт в DLQ.
5. Webhook получает HTTP POST. Успехом считается любой `2xx`. Общий лимит времени
   HTTP-операции по умолчанию 5 секунд, дополнительно действуют I/O-таймауты.
   Проверяется статус ответа, его тело не скачивается. Redirect не выполняется,
   `3xx/4xx/5xx` и сетевые ошибки считаются
   неудачной доставкой. Успех фиксируется в `webhook_delivered_at` до ACK.
6. При ошибке consumer одной транзакцией увеличивает `attempts` и записывает
   новое событие в outbox. Для повторов используется `available_at`, без удержания
   consumer в `sleep` и без RabbitMQ-плагинов. Первая попытка сразу, вторая через
   2 секунды после ошибки, третья через 4 секунды после следующей ошибки.
   Реальный запуск может быть позже из-за polling и загрузки очереди.
7. После третьей ошибки та же транзакция записывает `dead_lettered_at` и событие
   в outbox для `payments.dlx` -> `payments.dead`. Поэтому сбой брокера во время
   передачи в DLQ не теряет событие. ACK исходного сообщения выполняется после
   коммита retry/DLQ. Невалидные сообщения отклоняются и попадают в DLQ через
   `x-dead-letter-exchange` основной очереди.

Три попытки означают **первую попытку плюс два повтора**, а не четыре обработки.
Счётчик хранится в БД; старое сообщение не начинает цепочку заново. При ошибке
webhook уже завершённый платеж не отправляется в шлюз повторно. Если недоступна
сама БД и нельзя зафиксировать результат попытки, выполняется NACK/requeue с
паузой 1 секунда; такой инфраструктурный сбой не расходует счётчик без записи в БД.
Отмена consumer, в том числе во время этой паузы, возвращает сообщение в очередь.

`attempts` - число зафиксированных завершений попыток consumer, включая успешную.
`dead_lettered_at` означает, что передача в DLQ надёжно запланирована в outbox;
фактическая публикация может ждать восстановления брокера.
`last_error` хранит категорию ошибки и HTTP-код, без URL и содержимого ответа.
Если все три вызова шлюза завершились техническим исключением, статус остаётся
`pending`, а `dead_lettered_at` показывает необходимость ручного разбора. Бизнес-
статус не подменяется отказом доставки уведомления.

### Семантика доставки и сбои

Доставка **at least once**. Если брокер подтвердил publish, но процесс умер до
коммита `published_at`, relay опубликует событие ещё раз с тем же `message_id`.
Обработчик сверяет номер попытки и финальные маркеры под блокировкой строки.
Дубликаты завершённых попыток пропускаются.

Webhook содержит стабильный `event_id = payment:<UUID>:result`; такой же ключ
передаётся в заголовке `Idempotency-Key`. Получатель должен дедуплицировать его.
Если HTTP-получатель уже применил уведомление, а consumer умер до коммита,
уведомление придёт повторно. Exactly-once через PostgreSQL и произвольный HTTP
не обещается. Настоящий платёжный провайдер тоже должен принимать idempotency key:
в тестовом эмуляторе нет внешнего денежного побочного эффекта, а при реальном
шлюзе сбой между списанием и записью в БД потребует дедупликации у провайдера.

Relay работает внутри API, отдельный процесс не требуется. Несколько экземпляров
API безопасно делят outbox через `SKIP LOCKED`. Если все API остановлены, прием
новых запросов и публикация отложенных retry приостановлены до запуска API.

## Локальный webhook и сквозная проверка

Демонстрационный получатель доступен контейнерам как `http://webhook:8001`:

| Путь | Поведение |
| --- | --- |
| `/ok` | Всегда `204` |
| `/flaky` | Два ответа `503`, затем `204` для данного платежа |
| `/fail` | Всегда `503`, после трёх попыток событие уходит в DLQ |
| `/slow-once` | Первый ответ задерживается на 30 секунд, последующие `204` |
| `/events/{payment_id}` | Полученные уведомления и времена получения |

Это вспомогательный сервис без авторизации, только в профиле `demo`; данные
хранятся в памяти. Его код не входит в основной Docker image и монтируется отдельно.
Демонстрационные данные искусственные, реальные платежи не выполняются.

Для тестов на хосте нужен [uv](https://docs.astral.sh/uv/):

```sh
uv sync --frozen
uv run python -m scripts.smoke
uv run python -m scripts.smoke --faults
```

`--faults` останавливает и запускает **RabbitMQ и consumer этого Compose-проекта**:
проверяет прием платежа при недоступном брокере, доставку после восстановления,
а затем SIGKILL consumer во время webhook и безопасную повторную доставку.
Не запускайте этот режим на обслуживающем реальные запросы стенде.

## Автоматические тесты

Тесты используют настоящий PostgreSQL в отдельной БД `payments_test`. Шлюз и HTTP
в pytest заменены контролируемыми ответами, чтобы обе ветки 90/10 и ошибки были
детерминированными. Реальные RabbitMQ, HTTP, процессный рестарт и задержки
проверяет `scripts.smoke`. Тесты не очищают основную БД `payments`.

Создать тестовую базу нужно один раз:

```sh
docker compose exec -T postgres createdb -U payments payments_test
DATABASE_URL=postgresql+asyncpg://payments:payments@localhost:55432/payments_test uv run alembic upgrade head
uv run python -m pytest -q
uv run ruff check .
uv run ruff format --check .
DATABASE_URL=postgresql+asyncpg://payments:payments@localhost:55432/payments_test uv run alembic check
```

Тесты очищают только таблицы указанной тестовой базы перед каждым кейсом.
Для другой тестовой БД задайте `TEST_DATABASE_URL`; имя обязано оканчиваться
на `_test`. Миграции примените к тому же URL через `DATABASE_URL`.
Если меняете опубликованные порты Compose, задайте соответствующие
`DATABASE_URL`/`RABBITMQ_URL` для локальных проверок.

## Структура

```text
app/
  api.py           HTTP, API key, lifespan relay
  payments.py      Идемпотентное создание и атомарный outbox
  processing.py    Шлюз, webhook, сохранение retry/DLQ
  consumer.py      Единственный FastStream handler, ACK/NACK
  outbox.py        Подтверждённая публикация и восстановление соединения
  messaging.py     Топология RabbitMQ
  models.py        payments и outbox
  schemas.py       Pydantic-контракты
  config.py        Настройки
  db.py            Async engine/session
migrations/        Alembic upgrade/downgrade
tests/             Регрессии API, обработки и outbox на PostgreSQL
demo/              Локальный HTTP-получатель
scripts/           Генерация .env и сквозная проверка
```

## Настройки и ограничения

`API_KEY` обязателен, минимум 16 символов. Дополнительно: `DATABASE_URL`,
`RABBITMQ_URL`, `OUTBOX_POLL_SECONDS` (0.5), `RETRY_BASE_SECONDS` (2),
`WEBHOOK_TIMEOUT_SECONDS` (5). В Compose retry настраивается через `.env`;
остальные значения можно добавить в общий `environment` сервисов.
Порты настраиваются `API_PORT`, `POSTGRES_PORT`, `RABBITMQ_PORT`,
`RABBITMQ_UI_PORT`, `WEBHOOK_PORT`.

Это ограниченный локальный стенд по ТЗ: один доверенный API-клиент, один брокер,
один активный consumer. HTTP webhook может указывать на внутреннюю сеть, что
нужно для демонстрации. Для публичного сервиса понадобятся ограничения исходящих
адресов с защитой от DNS rebinding/SSRF, TLS и подпись webhook, индивидуальная
авторизация клиентов, HA брокера/БД, метрики, политика хранения outbox и процедура
ручного разбора DLQ. Эти свойства здесь не заявлены как реализованные.

Для простоты один consumer держит блокировку конкретного платежа во время шлюза
и HTTP-запроса. Это ограничивает параллелизм и время открытой транзакции, но
соответствует требованию одного обработчика и защищает от конкурентных дублей.

Остановка с сохранением данных:

```sh
docker compose --profile demo down
```
